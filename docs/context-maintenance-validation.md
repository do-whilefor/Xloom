# Wiki、检索与上下文维护验证

2026-09-16，Node v24.18.0。依据本地 Webounty Wiki 评审、`上下文.md` 和
《Grounding Agent Memory: Environment-Probing Curation for Enterprise Agents》提出的问题，
本批改动落实来源复核、历史按需读取、任务核心保留及检索开销边界。
论文中的 probing 用于验证记忆的适用性，并不证明某种压缩算法在 Xloom 更优；本次没有
增加角色、hook、向量服务或模型参数微调，既有角色系统提示词保持原样。

## 实现与验证范围

- 缺失条件：空值、unknown、unspecified、not_recorded、未知/未记录/未确认归一为未知；
  不能通过字符串相等被当作共同已知条件，不改写旧数据库。
- Wiki：明确因果前提的更正/缺失传播到派生 Fact；复核标记出现在原生读、搜索和投影。
  明确更正旧派生判断后可使用新前提，旧来源及冲突仍保留。
- 上下文：Fact 导航最多 16,000 字符，保留必需完整依赖和全部用户 Hint；历史分页覆盖
  省略项。Decide/元认知保留相关 Attempt 及最近 12 条，不能以省略判断未曾测试。
- 压缩：先去除连续只读片段里的完整重复原生读取，从当前黑板重建任务核心，再视容量
  调用摘要；少量已校验原件读取原样保留。压缩后重置本轮阅读覆盖，不重放工具操作。
- RAG：查询虚词过滤、导航与证据依赖分开、已知 ID 本地直达。语义提示逐步补全，
  每次最多 8 个判断；重排最多 12 个候选，两阶段输入各不超过 48,000 个 JSON 字符。
  超大完整来源包延后处理；缓存、来源变化、取消和失败降级仍使用既有原生读取器。

这是稀疏活动依赖的示例；大量必需前提、活动分支或用户原文仍须保留，不受上述历史
导航预算限制，不能外推为任意任务的固定上下文上限。

用故意丢弃标识和条件的模拟摘要器，连续压缩 3 次，每轮验证原文约束、最新身份更正、
同一原件包和完整工具调用/结果仍保留。另一个 12 次重复读取的样本移除 10 个重复批次，
保留最近两批；序列化消息由 111,180 降至 6,751 字符，摘要调用为 0。
这些原件包由 fixture 模拟，不是一次在线证据完整性审计。

`wiki-semantic.test.ts` 使用 29 个 Wiki 判断的冷缓存验证：第一次补全 8 个，延后 21 个，
扩展/索引/重排各 1 次。第二次复用前 8 个并补全另外 8 个；全部补全后的相同查询为
0 次模型请求。还验证已知 ID 查询为 0 次调用，以及超 48,000 字符的多块来源闭包
不被截断送入模型，本地交付仍保留所有条件。没有调用实际配置模型来验证这批改动。

无关虚词加不存在的标识返回 0 命中；否定、错误码、技术标识和精确引用有单独回归。
既有 20 例检索评估中，development 和 acceptance 各 10 例，Recall@5 均为 1；不存在
查询、来源/条件、字节定位检查均通过，黑板内容未变。这只检查固定语料下的候选、
来源与字节定位，不能视为真实问答准确率。

## 未经本批验证的结论

没有测量真实研究任务成功率、端到端模型回答质量、供应商计费 token 节省或长期记忆
准确率。没有训练压缩器，也没有新增自动目标探测。下一步应使用同一模型、同一任务
样本对比完成质量、漏条件率、重复操作率和实际总 token，再决定是否需要专用压缩模型。
